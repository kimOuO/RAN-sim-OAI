# 結果:D0 —— o1-adapter 本機建置與驗證(不接 SMO)

日期:2026-09-29。執行:DT 端,本機 10.3.0.217。結論:**通過**。
目的:確認 OAI o1-adapter 能在本機 build、起得來、能從 telnet 假 gNB 拉資料填進 NETCONF datastore、NETCONF 能登入。VES 全關,沒有碰 SMO。

## 環境
- 映像:`adapter-gnb:latest`(官方 Dockerfile.adapter,317 MB)→ `adapter-gnb:dt`(我方薄層,見下)。假 gNB:`oai-telnet-server:latest`(官方 `integration/telnet`,內容是 CU-CP 版 `cu_servertest.py`)。
- 位置:`02_測試/o1-adapter-dt/`(`docker-compose.d0.yml`、`config/config.json`、`Dockerfile.dt`)。
- 對外埠:NETCONF SSH 1830→830、SFTP 1222→22。

## 踩到的問題與處置
| # | 現象 | 原因 | 處置 |
|---|---|---|---|
| 1 | `docker build` 報 `unknown flag: --progress` | 本機 docker 29.1.3 無 buildx,官方 build 腳本帶 `--progress=plain` | 直接下 `docker build --target adapter-gnb ...` 不帶該旗標 |
| 2 | adapter 啟動即退出:`config json parser error: granularityPeriod` | `integration/config/config.json.template` 比程式少 `info.granularityPeriod`、`info.fileReportingPeriod`;模板路徑也要絕對路徑 `/adapter/config/...` | 以 `docker/config/config.json` 為準補齊 |
| 3 | `not found: BWP` | 官方 telnet 映像跑的是 **CU-CP** 假體,而 `unit-type: gNB` 會用 DU 解析器 | D0 改 `unit-type: "CU-CP"`;之後 DT 自己的 facade 要決定 node type(見下) |
| 4 | `Not found node "PerfMetricJob"`,datastore 空,且每秒 `[ERR] Invalid character` | 官方 `install-yangs.sh` 沒開 `_3gpp-common-managed-element` 的 feature **MeasurementsUnderManagedElement**,但程式會寫 `ManagedElement/PerfMetricJob`;失敗後殘留未初始化字串造成後續亂碼 xpath | 新增 `Dockerfile.dt`:`FROM adapter-gnb:latest` + `sysrepoctl -c _3gpp-common-managed-element -e MeasurementsUnderManagedElement`(feature 不能在 netopeer2/adapter 跑著時改,所以做成映像層) |
| 5 | `granularityPeriod` 0 超出 YANG range | 同 #2 補的值 0 不合法 | 設 900 |
| 6 | 每秒 `curl_easy_perform() failed ... 127.0.0.1:9` | 我刻意把 VES url 指向黑洞;`heartbeat-interval: 0` 仍會送 | 預期行為,接 SMO 時換成真 URL |

## 驗證結果
- `ssh -p 1830 netconf@127.0.0.1`:banner `SSH-2.0-libssh_0.9.2`,密碼登入成功,`netconf` subsystem 回 `<hello>`(2926 bytes,含 writable-running / candidate / validate 等 capability)。
- `sysrepocfg -X -d running -m _3gpp-common-managed-element`:已填 `ManagedElement=dt-o1-localtest` → `PerfMetricJob`(granularity 900,metrics `DRB.MeanActiveUeDl`)、`AlarmList`(internalConnectionLoss CLEARED)、`GNBCUCPFunction=0`(gNBId 1234、PLMN 001/01)→ **兩個 `NRCellCU`**(cellLocalId 10,sst 1/2)各帶 `NRFreqRelation`。
- adapter 每秒對假 gNB 下 `o1 stats` 正常。

## 對後續的意義
- **CU-CP 模式原生支援多個 NRCellCU**(從 telnet JSON 的 `NRCELLCU[]` 陣列來)。之前「一顆 adapter 只一個 cell」的限制是 DU 模式(`NRCellDU=0` 硬編碼)。DT 的 facade 可考慮:CU-CP node 給多小區清單,DU node 給頻寬/BWP/PCI。
- 官方 config 模板與程式不同步,以 `docker/config/config.json` 為準。
- 下一步 D0b:把 `ves.url` 換成 `http://10.3.0.204:30417/eventListener/v7`、`pnf-registration: true`、`node-id` 用 meid,送第一筆真實 pnfRegistration —— **等使用者放行與命名定案**。
