# (DT) N3 T3 劇本草案:「先低負載、再升高」—— 驗 rApp 自動下 policy 關 cell、再自動撤回開 cell(LIVE)

- 日期:2026-10-01 09:35Z;給 SMO / RIC 討論,**定案與切 LIVE 都要 mitlab 核准**

## 1. DT 的限制與做法
- 場域的人流(UE 數、路徑、在場時段)是預先計算的通道快取,**不能加人、不能改路徑**,`ue_count` 只能往下裁。
- 可以在 run 中改的是**每個 UE 的流量**:CU 的 `SessionController/update_traffic_profile`(`cbr`,`rate_mbps`),UE 端每次同步會讀 CU 的 profile 套進流量產生器;UE 進出場時 UE driver 會重推劇本提示,所以腳本每 20 秒重套一次。
- 腳本:`02_測試/n3_t3/t3_load.py <rid> '[[0,0.2],[900,4.0],[1800,0.2]]'`(秒 → Mbps)。

## 2. 劇本
| 項目 | 內容 |
|---|---|
| 場域 | `corridor24_16_24`(e30 src / e31 nbr / e32 mid,與 N2a 相同;rApp scope `corridor`) |
| run 長度 | 2400 秒(40 分鐘),PM 60 秒 |
| 階段 A(0–15 分) | 全部 UE 0.2 Mbps → 三個 cell PRB 預估 < 10 %,連 3 期 < 30 % 後 rApp 應選 UE 最少的 cell(多半 mid)下 policy;RIC es-on → 該 cell 的 UE 經 Xn 搬走、cell 關;O1 看到該 cell operationalState=DISABLED |
| 階段 B(15–30 分) | 全部 UE 4 Mbps → 剩下兩個 cell PRB 預估 > 70 %(T2 先量,不夠就 6 Mbps);連 2 期 > 70 % 後 rApp 應 DELETE;RIC es-off → cell 開回、UE 回流 |
| 階段 C(30–40 分) | 回 0.2 Mbps;冷卻 5 分鐘後 rApp 可能再進入節能(觀察第二輪);run 自動停,rApp 因 ME 斷線撤除 |

## 3. 驗收點
1. rApp 進入節能的時刻與候選(預期 ≈ 開始後 4–5 分鐘,候選 = 當時 UE 最少且 ENABLED 的 cell);
2. PUT → RIC es-on → cell 關閉 ≤ 5 秒;O1 operationalState=DISABLED;PM 該 cell 歸零、鄰 cell 上升;
3. 覆蓋洞保護:若 UE 合計掉到基準 50 % 以下(關 nbr 時會),rApp 應提前撤 —— 這場候選多半是 mid(覆蓋重疊大),預期不觸發;
4. 階段 B:rApp DELETE → es-off → cell 開回 ≤ 5 秒;UE 回流;
5. 全程 SDNR 無殘留告警;收場 ME 下線 rApp 撤除;
6. 三方時間一致(PUT / DELETE / es-on / es-off / CM 狀態變化)。

## 4. 前置
- **T2 校正(dry-run)**:先用同一腳本跑一場看 PRB 實際值(0.2 Mbps 與 4 Mbps 時各多少),調 rate 讓 A 期 < 30 %、B 期 > 70 %。DT 可在 10/1 之後任何時段跑,SMO 看 rApp 日誌即可。
- LIVE 前 mitlab 核准;RIC 側不需改(policy 由 rApp 經 PMS 下,xApp 照 N2a)。
- 新計數器(G9)上線後,rApp 可把 `RRC.ReEstabAtt` 升高加進退出條件,T3 同場一起觀察。

## 5. 待三方決定
- 階段 B 的 rate(4 或 6 Mbps)→ T2 後定;
- 是否刻意讓候選落在 nbr(用 FORBID 或 ue_count 裁減)以驗覆蓋洞保護 → 建議第二場再做;
- run 時間。
