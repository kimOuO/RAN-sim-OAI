## A. 劇本(scenario)層的隔離與資料收集

背景:DT 裡不同劇本的 gNB 彼此看不到對方(各自獨立的模擬世界)。SMO 不知道這層關係,它看到的是一群接在同一個 RIC、同一個 PLMN 底下的 gNB。mitlab 之後要「以劇本為單位」收集資料。

| # | 項目 | 說明 | 狀態 |
|---|---|---|---|
| A1 | SMO 端的資料無法直接按劇本切 | InfluxDB 的 PM、SDNR 的告警只帶 ME 名稱,沒有劇本或 run 編號。ME 名稱又會被不同 run、不同劇本重用(區塊釋出後再分配)。要按劇本收資料,目前只能用「ME 名稱 + 時間區間」去對。 | 未開始 |
| A2 | run 紀錄對照表 | 2026-10-01 完成:編排服務每次啟動 / 停止寫一行到 `run_logs/_o1_run_registry.jsonl`(runId、劇本、ME 清單、時間、結束原因);先前 12 次 run 由通知檔補回;查詢工具 `02_測試/run_registry/run_registry.py`(list / windows / flux)。 | 完成 |
| A3 | PM / 告警帶上劇本資訊 | 讓資料本身可按劇本查。可行方向(待與 SMO 討論):PM XML 的 `dnPrefix` 或 `measObjLdn` 帶 run;VES 事件標頭帶 run;或 SMO 入庫時依 A2 的對照表補標籤。 | 未開始 |
| A4 | 拓樸沒有劇本邊界 | TEIV 是一張平的圖,不同劇本的 gNB 並列,沒有標示彼此不相鄰。目前 SMO 只建 E2 / F1 連線,沒有建鄰區關係,所以暫時不會畫出錯的鄰接。之後若有 rApp 依拓樸推導鄰區或做跨 gNB 的最佳化,會把不同劇本的 gNB 當成同一張網。 | 未開始 |
| A5 | A1 policy 的作用範圍 | 所有 gNB 都歸在 `ric-dt-71` 底下。policy 若以 RIC 為單位下發,會同時作用到所有劇本。做 A1 閉環時要能把 policy 限定在一個劇本的 gNB。 | 未開始 |
| A6 | 同時多劇本未實測 | 到 2026-09-30 為止都是一次一個劇本、3 個 gNB。命名與埠不會撞(每個劇本一個區塊),但 SMO 控制器、SDNC 在多劇本同時上下線時的行為沒有驗過。SMO 控制器的設計目標是 20–30 個 ME 同時在線。 | 未開始 |
