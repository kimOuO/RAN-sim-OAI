# O1 對接初步計畫(SMO 已在另一台機器)

日期:2026-09-28
前提:SMO 已由對方部署在別台主機;DT 端(本機 10.3.0.217,ransim-platform)負責提供 O1 managed element。
上一份文件:`O1_SMO_可行性研究_2026-09-28.md`(路線 A = telnet 假面 + OAI o1-adapter)。

## 1. 需要對方 SMO 團隊提供的資訊(缺一項就卡一個環節)

### 1.1 SMO 是哪一套、哪一版
| 問題 | 為什麼要 |
|---|---|
| SMO 是 O-RAN SC OAM(SDNC/ODL + VES collector)、ONAP 完整版,還是商用/自研? | 決定 pnfRegistration 格式、NETCONF client 行為、要不要 SFTP 取 PM 檔 |
| Release / 映像版本(例:OAM K/L release、SDNC 2.7.x) | OSC 各版 VES schema 與 mount 流程有差 |
| 有沒有 Keycloak/OAuth 擋在前面 | 決定 VES 與 RESTCONF 的認證方式 |

### 1.2 網路與位址
| 問題 | 為什麼要 |
|---|---|
| SMO 主機 IP(與 10.3.0.0/24 是否同網段、中間有無防火牆/NAT) | adapter 走 host network,SMO 必須能**反向**連進 DT 的 NETCONF 埠 |
| VES collector URL(例 `https://<ip>:8443/eventListener/v7`)、是 HTTP 還是 HTTPS、憑證是否自簽 | adapter 出向送 pnfRegistration/heartbeat/fault/fileReady |
| VES 帳密(OSC 預設 sample1/sample1) | 同上 |
| RESTCONF 位址與帳密(例 `http://<ip>:8181/rests/...`,admin/…) | 若自動註冊失敗,我方要能手動 create-device 掛載與自查 |
| ODLUX 網址、帳號 | 我方驗證 DU 是否出現、看 PM/告警 |
| 對方可開放的入站埠範圍 | 我方 NETCONF 用 `1830+slot`、SFTP `122+slot`,多 run 會用多個埠 |

### 1.3 NETCONF 與模型期待
| 問題 | 為什麼要 |
|---|---|
| NETCONF 傳輸:SSH 830 還是 TLS 6513?要不要 call-home? | o1-adapter 兩者都可,但憑證要對得上 |
| NETCONF 帳密或是否要我方匯入 SMO 的 client 憑證 | pnfRegistration 內會帶帳密給 SDNC 反連 |
| 期待的 YANG:只要 3GPP `_3gpp-nr-nrm-*` Rel-18(o1-adapter 內建 30 支),還是也要 O-RAN `o-ran-*` 模型? | 決定路線 A 夠不夠,還是直接走路線 B |
| 想看到幾個 ME:每 gNB 一個、每 DU 一個、每 cell 一個? | 路線 A 一顆 adapter 只 1 個 NRCellDU |
| 要不要 CU-CP/CU-UP 節點,還是只要 DU | o1-adapter 有四種 node_type |

### 1.4 PM / FM 期待
| 問題 | 為什麼要 |
|---|---|
| PM 要檔案式(15 min XML + SFTP)還是 VES measurement 事件?粒度多少? | 決定聚合器怎麼寫;OSC 預設吃 fileReady |
| 想要哪些量測名(28.552)?先給 10 個 | 我方 190 個計數器裡挑 real 的對上 |
| 告警要哪幾種、嚴重度規則 | DT 目前沒有告警物件,要新建 |
| SMO 端會不會下 CM(改頻寬/鎖小區/改 A3),還是只讀 | 只讀的話路線 A 幾乎零改 DT |

### 1.5 時程與環境
- 對方能配合聯調的時段、聯絡窗口。
- 要不要我方先給一份 telnet 假面 + adapter 的 docker compose 讓對方在自己那邊先掛一次。

## 2. DT 端我方要先做的事(不等對方答覆也能動)

| # | 工作 | 產出 | 估時 |
|---|---|---|---|
| 0 | 在本機 build o1-adapter 映像,先用它自帶的 `servertest.py` 假 gNB + 本機臨時 SMO(或 NTS)驗一次流程 | 可用映像、已知坑清單 | 0.5–1 天 |
| 1 | 寫 `o1-telnet-facade`(Python asyncio,port `9090+slot`):把 CU `E2/NodeInfo/read`、CellConfig、DU `get_runtime_phys`、`E2FullReporter/read` 組成 OAI `o1 stats` JSON;`stop/start_modem` 對到 `MacCellController/disable|enable`;`bwconfig` 先記錄回 OK | 容器 + compose 區塊 | 1–2 天 |
| 2 | o1-adapter `config.json` 模板化:`node-id=meid`、`gnb-du-id`、`netconf-port=1830+slot`、`ves.url` 由 env 帶入 | 模板 + entrypoint | 0.5 天 |
| 3 | orchestrator `ROLES` 加 `o1adapter`(與 e2adapter 同 spawn 模式、host network) | 每 run 每 gNB 自動起 | 1 天 |
| 4 | PM 對表:把 o1-adapter 支援的 14 個量測對到 FullKPM 欄位,寫進 facade 的 `O1-Operational` 或改 adapter 的 pm_data | 對照表 + 實作 | 1 天 |
| 5 | 文件:`docs/api/o1_interface.md`(給 SMO 團隊的接口說明,格式比照 `e2sm_fullkpm.md`) | 文件 | 0.5 天 |

## 3. 聯調步驟(拿到 §1 資訊後)
1. 本機 `curl` SMO 的 VES 與 RESTCONF 位址,確認雙向可達;請對方從 SMO 主機 `nc -zv 10.3.0.217 1830`。
2. 起一顆 adapter,送 pnfRegistration,ODLUX 看到 DU 節點(記得第一筆常漏,重送一次)。
3. RESTCONF `GET .../yang-ext:mount/_3gpp-common-managed-element:ManagedElement=<meid>` 讀到 NRCellDU 屬性,對照 DT CellConfig。
4. 15 min 後確認 `fileReady` 與 SFTP 取檔;或縮短 `pm-data-interval` 先測。
5. 停掉 DU 容器,SMO 應收到 `softmodem-o1adapter-connected` MINOR 告警;恢復後 CLEAR。
6. 若對方要 CM:SMO 改 `bSChannelBwDL`,確認 facade 收到 `bwconfig`。
7. 開兩個 run,確認兩顆 ME 用不同埠、不同 meid 各自出現。

## 4. 已知風險
- 網段/防火牆:SMO 反連 NETCONF 是最常卡的一步;若不能開入站,只能改用 call-home(o1-adapter 目前未實作,要走路線 B)。
- o1-adapter 單 cell 硬編碼;多 cell 展示得一 cell 一 adapter。
- VES 第一筆遺失、SDNC STAGING 映像版本漂移。
- 記憶體:本機再加 N 顆 adapter(netopeer2+sysrepo 約 100–200 MB 一顆)尚可;SMO 不在本機是好事。
