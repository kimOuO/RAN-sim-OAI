## T1 哪一個候選效果最明顯、最容易重現

**負載平衡最適合,DT 同意 SMO 的傾向。**

| 候選 | DT 的看法 | 依據 |
|---|---|---|
| A 負載平衡 | 現成場景 `corridor24_16_24` 就有穩定的不平衡:nbr(e31)PRB 約 43–49 %、UE 6–9 個;src(e30)約 21–28 %、UE 2–3 個;mid(e32)約 7–8 %、UE 0–1 個。今天六場 run 都是這個樣子,可重現 | 實測(PM 與逐秒紀錄) |
| B 流量導引 | 做得到,但 UE 在這個場景裡停留時間短(見 T2),指定單一 UE 的 policy 容易在下達時 UE 已不在該 cell | 實測(今天 RIC 的 3-1 前兩輪都因此落空) |
| C 節能 | gNB 支援 cell 鎖定 / 解鎖與節能開關,但 DT 的 O1 沒有上報能耗類量測(`PEE.*` 未支援),SMO 看不到效果;要做得先補量測 | 讀碼;O1 現況 |

提醒一個 A 的風險:不平衡的成因是 UE 的位置與移動(UE 自己往 nbr 那一帶走),不是參數設錯。把 UE 換到較空的 cell 後,訊號較差的 UE 可能很快又回來或斷線重建(T2)。所以「兩個 cell 的 PRB 使用率靠近」能不能維持,要實際跑才知道。

## T2 gNB 接受哪些 E2 控制;換手後 UE 會不會被帶回去

接受的控制(RIC 閘道對這個場景登記的清單,**實測**過的標 ✓):

| 控制 | 作用 | 今天實測 |
|---|---|---|
| RC 3-1 | 單 UE 換手 | ✓ 成功回 ACK;失敗回 Failure + IE 32 |
| RC 3-1-group | 群組換手(一次多個 UE) | 未在今天的 run 驗 |
| RC 2-6 | PRB 配額(可限定單一 cell) | ✓ ACK(RIC 的 dt-exec 自動送的) |
| RC 2-8 | 天線 / 波束(傾角、波束、層數) | 未驗 |
| CCC lock / unlock | cell 停用 / 啟用 | ✓ ACK |
| CCC es-on / es-off | 節能模式 | 未驗 |
| ANR add / remove / flag、ReportCGI | 鄰區關係管理 | 未驗 |

**會被帶回去。** 模擬器的 UE 依場景的移動模型走,換手判斷是 gNB 自己的 A3 事件:

- 有鄰區關係時:UE 被 RIC 換到訊號較差的 cell 後,A3 條件成立就會換回去。
- 沒有鄰區關係時(今天的 run 都是 `anr_auto_add=false`、鄰區表是空的):UE 無法正常換手,移到邊緣只能斷線後在別的 gNB 重建。今天實測每個 UE 每 1–2 分鐘就換一次 cell。
- 今天 13:08Z RIC 手動換的那一筆(p03 → nbr),2 秒後 CU 就收到換手報告,判為 TooEarly。

對負載平衡的意義:只靠「把 UE 換過去」不會持久。比較可行的是調整讓 UE 自己留在目標 cell 的參數(例如 cell 個別偏移),或用 PRB 配額(2-6)限制來源 cell。gNB 目前有沒有可經 E2 調整的換手偏移,**未確認**,DT 會查了再補充。這一點也請 RIC 在 R5 一起看。

建議:A1 驗證用的 run 打開 `anr_auto_add`(或預建鄰區關係),否則 UE 的流動太亂,看不出 policy 的效果。

## T3 PM 夠不夠驗「效果」;週期能不能縮短

15 分鐘的週期確實看不出過程。三個做法:

| 做法 | 說明 | 注意 |
|---|---|---|
| 縮短 PM 週期 | DT 的 o1-adapter 週期是設定值(`O1_PM_INTERVAL`,預設 900)。09-29 聯調初期用過較短的週期,後來應 SMO 要求改成 900。驗證用的 run 可以改成 60 秒 | **SMO 先前說明轉檔程式把 `GranularityPeriod` 固定寫成 900、不讀 XML 的 `duration`**,而且檔名是到分鐘,60 秒是下限。SMO 端能不能正確處理 60 秒的檔,請 SMO 確認 |
| DT 提供逐秒對照資料 | DT 本來就有:轉接程式每秒一筆的 UE 數 / PRB 負載 / 吞吐(今天 PM 對值用的就是這個)、編排服務的每秒歸檔 | 這不經 O1,是離線對照用;SMO 的 rApp 讀不到 |
| 兩者並用 | O1 的 PM 用 60 秒給 rApp 當輸入,逐秒資料給人看過程 | DT 的建議 |

另外提醒:`DRB.MeanActiveUeDl` 是無條件捨去的整數,60 秒的週期下小 cell 會更常顯示 0;判斷負載請用 `RRU.PrbTotDl`。

## T4 cell 的識別

可以直接算:**NCI = gNBId × 2^14 + cellLocalId**(gNB ID 22 bit、local cell 14 bit,共 36 bit)。

| cell | gNBId | cellLocalId | NCI |
|---|---|---|---|
| e30:src | 3632(0xe30) | 0 | 59506688(0x38c0000) |
| e31:nbr | 3633 | 0 | 59523072(0x38c4000) |
| e32:mid | 3634 | 0 | 59539456(0x38c8000) |

PLMN 是 208 / 95(E2 上的編碼 `02f859`)。以上是今天從三個 CU 實際讀出的值,RIC 用它們送 3-1 成功(實測)。

兩個例外請留意:

- **常駐的 e00 不適用這個公式。** e00 的 cell 沒有填 NCI,CU 用 cell 名稱的雜湊當 NCI(src = 10736230946、nbr = 48206411369)。A1 驗證請用場景節點,不要用 e00。
- `cellLocalId` 這個場景是 0,不保證每個場景都是 0;請從 O1 讀,不要假設。今天 RIC 第一輪就是假設 1 而全部失敗。

## T5 UE 的識別(若選流量導引)

- gNB 這一側接受的 UE ID 是 E2 的 gNB-UEID:`amf_ue_ngap_id`(整數)加 PLMN。CU 也接受 gNB-CU-UE-F1AP-ID。
- UE 在模擬器裡的名稱是 `p00`–`p17`。
- **`amf_ue_ngap_id` 在今天的 run 之間是固定的**(例 p03 = 1320546915、p08 = 1114830132,六場 run 與常駐的 e00 都相同)(實測)。是不是保證跨場景固定,**未確認**。
- UE 斷線重建後 `amf_ue_ngap_id` 不變,會變的是 RAN 側的 ID(實測)。
- 限制:CU 只在「自己的 UE context」裡找這個 ID。UE 不在該 gNB 上時會回「找不到 UE」。SMO 沒有 UE 層資料,而 DT 的原則是 UE 位置不作為觀測資料提供(mitlab 先前的決定),所以流量導引需要的 UE 清單只能由 RIC 從 E2 的資料取得。

## 對階段順序的看法

- 同意 N1 與 N2 同時開始、N2 先做手動版。
- N2 對 DT 的工作:提供驗證用場景(開鄰區關係)、視需要把 PM 週期縮短、提供逐秒對照資料、每場 run 前通知 RIC 與 SMO。約半天,不含 T2 提到的「換手偏移是否可調」的查證。
- N5 的通知通道加密會動到 DT 的 o1-adapter 與編排服務的送端,工作量 DT 還沒評估。
- DT 自己另有一項與 N2 / N3 相關的缺口:SMO 的 PM 沒有劇本層,同時跑多個劇本時 rApp 會把不同劇本的 cell 當成同一張網。DT 已做了 run 對照表(`runId ↔ 劇本 ↔ ME ↔ 時間`),但那是離線對照;rApp 要即時分辨劇本的話,需要另外設計(例如 policy 的作用範圍限定在一個劇本的 cell 清單)。N2 只跑單一劇本時不受影響。
