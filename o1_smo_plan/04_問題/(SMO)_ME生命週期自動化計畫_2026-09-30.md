# (SMO) ME 生命週期自動化計畫：gNB 上線自動登記、劇本結束自動清理

- 日期：2026-09-30
- 來自：SMO 端（10.3.0.204）
- 狀態：**草案，待 DT 確認第 7 節的問題、待 mitlab 核准後實作**
- 相關文件：`01_計畫/ME生命週期與資料清理規則_草案_2026-09-29.md`（C1–C7 手動流程，本計畫取代其中的手動步驟）

## 1. 為什麼要做

目前 DT 每啟動一個劇本（run），SMO 端要手動做四件事；劇本結束要再手動做三件事。DT 的環境是「劇本」概念，一個劇本底下有多個 gNB 和 cell，可能同時啟動多個 gNB，手動做法跟不上，也容易漏清理而讓 SDNC 累積殘留連線。

| 時機 | 現在手動做的事 |
|---|---|
| 劇本開始 | ① PMS 登記 gNB 歸哪個 RIC ② NCMP 註冊 CM handle ③ 發佈 E2 / F1 連線關係到 TEIV（資料來自 DT 放的檔案） |
| 劇本結束 | ④ 逐筆刪連線關係 ⑤ 移除 NCMP CM handle ⑥ 刪 SDNC mount |

## 2. 規範定義到哪裡，缺了哪幾段

| 段落 | 誰定義 | 現況 |
|---|---|---|
| gNB 上線送 `pnfRegistration`（VES） | O-RAN WG10 O1（PnP）、ONAP VES 7.2.1 | ✅ 已走，自動 |
| SMO 收到後建立 NETCONF 連線 | O-RAN O1；ONAP SDNR 實作（自動 mount） | ✅ 自動 |
| PM / FM / 心跳上報 | O-RAN O1、3GPP TS 28.532 / 28.550 / 28.111 | ✅ 自動 |
| **gNB 下線（反註冊）** | **O1 的 PnP 沒有定義反註冊事件**。3GPP TS 28.532 的 Provisioning 通知有 `notifyMOIDeletion`，可用來表示「這個 ManagedElement 已移除」 | ❌ 沒有使用，現在靠 DT 放檔案通知、SMO 手動刪 |
| **SMO 內部：註冊事件 → NCMP 登記** | 規範不管 SMO 內部。ONAP 的設計是由上游庫存系統通知 DMI plugin 去註冊，但沒有現成元件把「pnfRegistration」接到「NCMP 註冊」 | ❌ 手動 |
| **SMO 內部：gNB 歸屬哪個 RIC（PMS）** | A1 規範只定義 policy 怎麼傳，沒有定義歸屬從哪裡來。PMS 的設計是靜態設定 | ❌ 手動 |
| NCMP → TEIV 節點 | O-RAN SC TEIV 的 adapter 機制 | ✅ 自動（本地修正版 adapter） |
| **TEIV 連線關係（E2、F1）** | TEIV 靠 adapter 寫入；官方的 adapter 只處理單一 ME 的內容，不處理跨 ME 的連線 | ❌ 手動，且資料來源是檔案不是 O1 |

結論：缺的是四段「接頭」：反註冊訊號、NCMP 自動登記、PMS 自動歸屬、連線關係自動推導。

## 3. 新系統：`o1-me-lifecycle-controller`

SMO 端新增一個小型控制器（smo namespace 的一個 Deployment）。**原則是只使用既有的官方訊號和官方 API，不新增任何非標準介面，DT 和 RIC 不需要直接碰 SMO 內部。**

### 3.1 基於什麼、改了什麼

| 缺的接頭 | 基於哪個既有訊號 / API | 控制器做什麼 |
|---|---|---|
| NCMP 自動登記 | Kafka `unauthenticated.VES_PNFREG_OUTPUT`（SDNR 自動 mount 用的同一個事件）＋ SDNC RESTCONF 的 mount 狀態 | 收到註冊事件 → 等 mount 變 connected → 呼叫 NCMP 註冊 API（多個 ME 合併成一次呼叫） |
| PMS 自動歸屬 | RIC 自己透過 O1 上報的 E2 節點清單（`o-ran-sc-ric-gnb-status-v1:ric/nodes`） | 讀每個 RIC 的清單，gNB 出現在哪個 RIC 且 `connected`，就登記到那個 RIC |
| 連線關係自動推導 | E2：同上的 RIC 清單。F1：CU 和 DU 各自上報的 `gNBId` / `gNBIdLength` / PLMN | E2：RIC 清單裡有這個 gNB → 建 E2 連線。F1：CU 和 DU 的 gNB 識別相同 → 建 F1 連線。以 CloudEvent 寫入 TEIV |
| 反註冊訊號 | 主要：VES `stndDefined` / `3GPP-Provisioning` 的 `notifyMOIDeletion`（VES collector 已有路由，topic `unauthenticated.SEC_3GPP_PROVISIONING_OUTPUT` 已存在）。備援：mount 斷線且心跳停止超過寬限時間 | 觸發清理流程（3.3） |

07:40Z 已實際查證上表的資料來源都存在，不需要 DT 或 RIC 改程式就能取得：

- RIC-A 的 O1 目前回報 4 個 E2 節點：`gnb_208_095_000e00`、`e30`、`e31`、`e32`，都是 `connected`，`ran-name` 和 SMO 的 ME 名稱一致。
- `gnb_208_095_000e30`（CU）和 `gnb_208_095_000e30_du1`（DU）的 CM 都回報 `gNBId = 3632`、`gNBIdLength = 22`，可以直接配對。

### 3.2 上線流程（自動）

```
gNB ─pnfRegistration→ VES → Kafka ─┬→ SDNR 自動 mount（既有）
                                   └→ controller
                                        1. 等 mount connected
                                        2. NCMP 註冊（批次）→ adapter 自動建 TEIV 節點
                                        3. 讀 RIC 的 E2 節點清單 → PMS 登記歸屬
                                        4. 節點出現後 → 發佈 E2 / F1 連線關係
```

### 3.3 下線流程（自動，順序固定）

```
收到 notifyMOIDeletion（或備援條件成立）
  1. 逐筆刪除這個 ME 的連線關係（一個事件一筆，每筆後確認 ingestion lag = 0）
  2. 移除 NCMP CM handle → adapter 自動逐筆刪 TEIV 節點
  3. 刪除 SDNC mount
  4. 從 PMS 的歸屬清單移除（該 gNB 沒有 policy 時）
```

順序和「一次一筆」是硬性規則：TEIV 的 ingestion 遇到一個事件含多筆刪除會永久卡住（已知問題，發生過兩次）。

### 3.4 對應 DT 的劇本概念

- 一個劇本可以有多個 gNB，可同時啟動：控制器用佇列處理，NCMP 註冊和 PMS 寫入都是批次、單一寫入者，不會互相覆蓋。
- 請 DT 在 `pnfRegistration` 的 `additionalFields`（規範允許的自由欄位）帶上劇本資訊，控制器會存成 NCMP 的公開屬性，之後可以「依劇本」查詢和清理：

| 欄位 | 範例 | 用途 |
|---|---|---|
| `scenarioId` | `corridor24_16_24` | 劇本名稱 |
| `runId` | `00bba8b4` | 這次執行的編號，同一 run 的 ME 一起清理 |
| `role` | `CU-CP` / `DU` | 節點角色 |
| `lifecycle` | `ephemeral` | 標示「模擬用、可自動清理」 |

- 劇本進行中個別 gNB 加入或離開也支援：每個 ME 獨立處理，不要求整個劇本同進同出。
- 控制器每 60 秒做一次對帳（比對 SDNC、NCMP、PMS、TEIV 四邊），漏掉事件或控制器重啟後會自動補齊。

### 3.5 安全防護

| 風險 | 防護 |
|---|---|
| 誤刪真實 RAN 或常駐節點 | 只自動清理 `lifecycle=ephemeral` 的 ME；`gnb_208_095_000e00`、RIC、未來的真實 RAN 列入保護清單，永不自動刪 |
| gNB 短暫斷線被當成下線 | 備援條件要「mount 斷線且心跳停止」同時成立並超過寬限時間（預設 10 分鐘）才清理；有 `notifyMOIDeletion` 時立即清理 |
| 一次刪太多 | 每輪清理有上限；TEIV 刪除嚴格逐筆 |
| 斷線的 ME 拖垮拓樸同步 | adapter 目前遇到已登記但斷線的 ME，整輪同步會失敗（07:12Z 發現）。列為前置修正 |
| 大量 gNB 同時上線壓垮 SDNC | 需要 DT 提供規模（第 7 節 D1），再定同時在線上限並檢查 SDNC 記憶體 |
| 上線初期行為不如預期 | 先以「只記錄不動作」模式與手動流程並行一到兩個 run，結果一致才開啟自動 |

## 4. 連線關係改由 O1 推導（原第 4 步）

| 連線 | 現在 | 改成 | 需要誰動 |
|---|---|---|---|
| E2（gNB ↔ RIC） | DT 放檔案，SMO 手動發佈 | 由 RIC 的 O1 E2 節點清單推導 | 只有 SMO。RIC-A 已有這份資料 |
| F1（CU ↔ DU） | 同上 | 由 CU / DU 上報的 gNB 識別配對 | 只有 SMO。DT 已有上報 |

驗證方式：並行期間，控制器推導的結果和 DT 檔案逐筆比對，連續兩個 run 一致後，DT 就不用再產連線關係檔。

長期：F1 配對邏輯適合放回 O-RAN SC 的 adapter，連同先前的修正一起回報上游。3GPP 的標準做法是上報 F1 端點物件（TS 28.541 的 `EP_F1C`），DT 的 YANG 已載入該模組但沒有填值，是否要補由 DT 評估（第 7 節 D6）。

## 5. 需要的權限（實作時請 mitlab 核准）

- 新增一個 Kafka 帳號：讀 `VES_PNFREG_OUTPUT`、`SEC_3GPP_PROVISIONING_OUTPUT`、心跳 topic；寫 `topology-inventory-ingestion`。
- 在 smo namespace 新增一個 Deployment，可讀 SDNC 帳密的 secret。
- 可呼叫 SDNC RESTCONF（讀 mount、刪 mount）、NCMP 註冊 API、PMS 設定 API。
