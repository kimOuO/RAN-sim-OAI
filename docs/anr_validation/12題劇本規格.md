### 0.2 平台層級的觸發門檻(所有題共用)

| 參數 | 值 | 意義 |
|---|---|---|
| `HO_A3_OFFSET_DB` / `HO_A3_HYSTERESIS_DB` / `HO_TTT_MS` | 2.0 / 1.0 / 300 | A3 換手門檻 = 鄰居強過服務 **3 dB 且持續 0.3 秒**。<br>**劇本內的 `a3_*` 會蓋掉這裡**,十二題劇本已統一寫成同值 |
| `ANR_REQUIRE_NRT` | true | NRT 沒有的關係不准換手 —— 缺漏鄰區之所以會痛的原因 |
| `MEAS_REPORT_MIN_RSRP_DBM` | -110 | 量測回報門檻(TS 38.331 `reportConfig`),低於此不回報 |
| `ANR_NRT_CAPACITY` | 8 | 每 cell NRT 條目上限(第9題用) |
| `ANR_INTRA_ENABLED` | true | ANR 自動建立功能開關(第2題停用分支用) |
| `ANR_XN_AUTO_REVERSE` / `ANR_XN_SETUP_DELAY_SEC` | on / 2.0 | ADD 後由 gNB 經 Xn 自動建反向(TS 38.300 §15.3.3.2 步驟 4c),延遲 2 秒 |
| `ANR_STALE_PCI_CHECK` | on | 關係存的 PCI 與 cell 實際不符 → `CellNotAvailable`(第10題) |
| `HO_FORCE_FAIL_TARGET` | 空 | 指定 target 的換手一律失敗(第7題注入用) |
| `E2SM_ANR_ENABLE` | on | ran_func=6 的 SON 觸發總開關 |

> 改 env 要 `docker compose up -d ransim-cu`;只改 Python 用 `docker restart ransim-cu`。

### 0.3 佈病腳本

前置條件(刪關係、改 PCI、填容量…)由 **`scripts/anr_arm.py`** 一鍵布好:

```bash
docker exec -i -e CASE=q6    ransim-cu python manage.py shell < scripts/anr_arm.py   # 布第6題
docker exec -i -e CASE=status ransim-cu python manage.py shell < scripts/anr_arm.py  # 看目前 NRT
docker exec -i -e CASE=reset  ransim-cu python manage.py shell < scripts/anr_arm.py  # 清病
```

**流程**:上傳/選劇本 → Start Sim → 跑佈病腳本 → 通知 RIC 開始 → 全程唯讀觀察。

### 0.4 xApp 拿得到的觀測面(func 6 一包)

`POST /api/v0.1/CU/Anr/AnrQueryActor/indication` 或 E2SM-ANR indication:

| 區塊 | 主要欄位 |
|---|---|
| `e2NodeInformation` | `servingCells`、`neighbourCellRelations`(含 `xnX2Established` / `hoValidated` / `version` / `relationAgeSec` / `flags`)、`frequencyRelations`、`anrIntraEnabled`、`nrtCapacity{limit,used}`、`relationChangeEvents{action,by,detail,reason}` |
| `kpmIndication` | cell 級 HO 速率/成功率、`RRU.PrbTotDl/Ul`、`perNeighbourRelation`(含**零活動關係**)、`handoverFailureCauseRatePerMin`、`cumulativeSinceCreation` |
| `rlfKpm` | RLF / 重建速率、`reestablishmentInboundByPreviousPci` |
| `mroKpm` | `TooEarly / TooLate / ToWrongCell` 速率 ⚠️ 見 §3 自我抹除 |
| `e2MessageCopyAggregate` | 依回報 PCI 的 RSRP 統計、`sourceCellNcgi` / `bySourceCell` |

輔助查詢:`cgi_resolve(pci[,arfcn])` → `{results, confusion}`。

### 0.5 平台提供的處置命令(E2SM-ANR ran_func=6 / RC ran_func=3)

| 命令 | 用途 | 成功 `result` | 失敗 `result` |
|---|---|---|---|
| `ADD` | 建關係 | `ADDED` / `UPDATED` | `ADD_REJECTED`(detail=`NRT_CAPACITY_REACHED`)、`REJECTED_ANR_DISABLED` |
| `REMOVE` | 刪關係 | `REMOVED` | `NOT_FOUND`、`REJECTED_PROTECTED`(noRemove) |
| `FLAG` | 設/清 `hoBlocklist`/`noRemove`/`xnBlocklist` | `FLAG_SET` / `FLAG_CLEAR` | `NOT_FOUND` |
| `REPORTCGI`(RC Style 9 / Action 1) | PCI → NCGI 解析 | outcome 帶 `physicalCellId` / `cgi` | `confusion=true` 代表撞號 |

### 0.6 ACK 長什麼樣(所有題共通)

E2 `RIC_CONTROL_ACK` 的 **`RICcontrolOutcome`(IE id=32)** 內含 UTF-8 JSON:

```json
{"requestType":"ADD","sourceCellId":"src_c0","targetCgi":"nbr_c0",
 "result":"ADDED","version":1,"detail":""}
```

- 修好前 ACK 只有 **22 bytes、沒有 outcome**,xApp 無法從 ACK 分辨成敗 —— 這是本輪修掉的真 bug;現在帶 outcome 的 ACK 約 **150 bytes**,可用 `len(ack)` 快速判斷版本。
- **零動作題(5/6/12)的正確 ACK 是「沒有 ACK」** —— 因為根本不該發控制命令。
- 觀察方法:`docker logs ransim-e2adapter | grep "ANR control outcome"`。

## 1~12 題逐題規格

### Q1 缺漏鄰區(重建統計反推) — `anr_missing_neighbor`

| 項 | 內容 |
|---|---|
| **怎麼觸發** | 刪掉 `src_c0 ↔ nbr_c0` 兩向關係(`CASE=q1`)。UE 東西向來回,A3 判到 nbr 但 `ANR_REQUIRE_NRT` 擋掉換手 → 掉線後重建到 nbr |
| **門檻** | A3 3dB/300ms;`ANR_REQUIRE_NRT=true` |
| **看什麼指標** | `rlfKpm.reestablishmentInboundByPreviousPci` 集中在 `prevPci=20`;`neighbourCellRelations` 查無此筆;`nrtCapacity used<limit`(排除容量) |
| **平台解法** | `REPORTCGI(pci=30)` → `ADD src_c0→nbr_c0` |
| **ACK** | `result=ADDED, version=1`;**2 秒後**自動出現反向 `ADD nbr_c0→src_c0`(審計 `by=gnb-xn`,非 xApp 所為) |
| **驗收** | RLF `3.33/min → 0`、HO `0 → 3.33/min`;`changeEvents` 一筆 `by=xapp` + 一筆 `by=gnb-xn` |

### Q2 缺漏鄰區(量測側偵測) — `anr_missing_meas`

| 項 | 內容 |
|---|---|
| **怎麼觸發** | 刪 `s25_c0→n35_c0`(`CASE=q2`)。**雙分支**:`ANR_INTRA_ENABLED=true` / `false` |
| **門檻** | 量測 gap ≤ MARGIN_HO;回報門檻 `MEAS_REPORT_MIN_RSRP_DBM=-110` |
| **看什麼指標** | `e2MessageCopyAggregate` 有 `pci=135` 樣本、`neighbourCellRelations` 無此筆、`anrIntraEnabled` 決定走哪支 |
| **平台解法** | 啟用 → `REPORTCGI` + `ADD`;**停用 → 只准 SMO_NOTIFY,不得自動寫 NRT** |
| **ACK** | 啟用 `result=ADDED`;停用 `result=REJECTED_ANR_DISABLED` |
| **驗收** | 啟用分支關係 v=1 且量測 gap 收斂;停用分支 `changeEvents` 恆 0 |

### Q3 缺漏鄰區(深邊緣稀疏) — `anr_sparse_edge`

| 項 | 內容 |
|---|---|
| **怎麼觸發** | 刪 `s28_c0→n91_c0`(`CASE=q3`);n91 位於 460/440m 深邊緣,UE 少數時段才走到 |
| **門檻** | 相對稀疏 —— n91 的樣本數遠低於其他鄰區 |
| **看什麼指標** | `meas_aggregate` 中 `pci=209` 的 `sampleCount` 明顯偏低;`nrtCapacity used<limit` 排除容量因素 |
| **平台解法** | 低樣本下**仍要** `REPORTCGI` + `ADD`(不可因樣本少就忽略) |
| **ACK** | `result=ADDED` |
| **驗收** | 關係建立、深邊緣 RLF 下降 |
| **⚠️ 折扣** | 卷面 0.6/min 的**絕對稀疏做不到**(sim 每 tick 每 UE 都記錄量測)→ 改用相對稀疏;`gap<0` 未達成;卷面「過半無法重建」的服務終止型外顯未重現 |

### Q4 未知 cell 偵測 — `anr_unknown_cell`

| 項 | 內容 |
|---|---|
| **怎麼觸發** | `unk_c0`(pci301)不在任何 NRT、也未被 seeder 種過(`CASE=q4`) |
| **看什麼指標** | 量測出現從未見過的 PCI;`cgi_resolve(301)` 解得唯一 NCGI 且關係表無此筆 |
| **平台解法** | `REPORTCGI(301)` → `ADD s01_c0→unk_c0` |
| **ACK** | REPORTCGI outcome `{physicalCellId:301, cgi:…}`;ADD `result=ADDED` |
| **驗收** | 關係出現、往 unk 的換手成功 |
| **⚠️ 折扣** | guard 166 秒就修好,**未觀察到止血衰減曲線**(病沒發作就治好) |

### Q5 PCI 撞號(擋) — `anr_pci_confusion`

| 項 | 內容 |
|---|---|
| **怎麼觸發** | 場景本身即病:`west_c7` 與 `east_c7` 共用 `pci=7`,DB 不用動(`CASE=q5` 只做確認) |
| **看什麼指標** | `cgi_resolve(pci=7)` 回 **`confusion=true`**、`results` 多鍵 |
| **平台解法** | **不得 ADD** —— 盲目 ADD 會建到錯的 cell。正解是抑制動作 + 通報 |
| **ACK** | **無 ANR control**(零動作即正解),只發 SMO_NOTIFY |
| **驗收** | `changeEvents` 恆 0、adapter ANR control 計數 0 |

### Q6 Xn-C TNL 探索失敗(不動手) — `anr_xn_discovery`

| 項 | 內容 |
|---|---|
| **怎麼觸發** | 把 `s07_c0→n33_c0` 的 `xn_x2_established` 設 False(`CASE=q6`):**關係在、Xn 不在** |
| **門檻** | 關係存在 → A3 照樣發起換手 → 沒有 Xn 傳輸 → 準備階段必然逾時 |
| **看什麼指標** | `neighbourCellRelations` 該筆 `xnX2Established=false`;失敗原因由 **`TXnRELOCprepExpiry`**(TS 38.423)主導 |
| **平台解法** | **不動手** —— Xn 建立屬管理面,xApp 不得用 ADD/REMOVE 掩蓋;只發 SMO_NOTIFY |
| **ACK** | 無 ANR control |
| **驗收** | `changeEvents` 0、關係 version 不變、SMO 告警一筆 |
| **注意** | 本題是換手失敗型,**會自我污染 MRO**;排除條件要用 `handoverFailureCauseRatePerMin`,不要用 `mroKpm.*Rate`(§3) |

### Q7 有害鄰居 — `anr_harmful_neighbor`

| 項 | 內容 |
|---|---|
| **怎麼觸發** | env `HO_FORCE_FAIL_TARGET=nbr_c0`(+`HO_FORCE_FAIL_CAUSE`,預設 `RandomAccessProblem`)。訊號看起來良好、換手一律失敗 |
| **門檻** | 注入式 —— sim 的 RSRP 模型做不出「訊號好但接入失敗」 |
| **看什麼指標** | `perNeighbourRelation src_c0→nbr_c0` 的 `succ→0`、`att` 持續;`handoverFailureCauseRatePerMin` 累積 `RandomAccessProblem` |
| **排除條件** | `max(TooEarly, ToWrongCell) ≤ 1.0`(**TooLate 不計** —— 它是本病的果不是因);來源與目標 PRB 皆 <85% |
| **平台解法** | `FLAG hoBlocklist set` —— **封而不刪**(關係還在,只是不讓換過去),保留日後復原空間 |
| **ACK** | `result=FLAG_SET`,`version` 遞增 |
| **驗收** | `hoBlocklist=True` 且 v+1;**反向關係零觸碰**;`RandomAccessProblem` 累計凍結;`att` 由 1.0 掉到 0 |
| **⚠️ 折扣** | 靠旗標注入,非物理自然產生 |

### Q8 跨頻鄰區啟用 — `anr_inter_freq`

| 項 | 內容 |
|---|---|
| **怎麼觸發** | 砍掉 `s11_c0` 對三個 2.1GHz cell 的關係(`CASE=q8`)→ **NRT 內整個頻率層不存在** |
| **看什麼指標** | `frequencyRelations` 缺 2.1GHz 那層(依 TS 28.541 由關係的 `target_arfcn` 推導,**不是列出所有 cell 的頻率**);量測有跨頻強 PCI |
| **平台解法** | 帶 `arfcn` 的 `REPORTCGI` ×3 → `ADD` ×3 |
| **ACK** | 三筆 `result=ADDED`,`targetArfcn` 為 2.1GHz 對應值 |
| **驗收** | `frequencyRelations` 出現 2.1GHz 層、三筆關係 v=1 |

### Q9 NRT 容量修剪 — `anr_nrt_capacity`

| 項 | 內容 |
|---|---|
| **怎麼觸發** | `CASE=q9` 把 n60/n61/n62 的 NRT 填到 `used==limit`(8),其中含零活動 `x24_c0` 與受保護 `x25_c0`(noRemove) |
| **門檻** | `ANR_NRT_CAPACITY=8` |
| **看什麼指標** | `nrtCapacity used==limit`;`changeEvents` 出現 **`ADD_REJECTED` / `NRT_CAPACITY_REACHED`** ← 證明「阻斷點在容量、不是偵測失效」 |
| **平台解法** | 先 `REMOVE` 零活動關係騰位,再 `ADD` 目標關係(**剪一補一**) |
| **ACK** | 被擋 `result=ADD_REJECTED, detail=NRT_CAPACITY_REACHED`;剪 `REMOVED`;補 `ADDED` |
| **驗收** | 完事後 `used` 仍 = limit(**8/8,不得 9/8**);受保護 `x25_c0` 未被碰;反向由 `gnb-xn` 建**且同受容量約束** |
| **注意** | `ADD` 的 `sourceCellId` 必須是既有 cell,**不可反過來拿待發現 cell 當來源** |
| **⚠️ 折扣** | RIC 首輪有一條關係是手動補的(已標記),重驗版為全自動 |

### Q10 過期對應(同站換 PCI) — `anr_stale_pci`

| 項 | 內容 |
|---|---|
| **怎麼觸發** | 關係 `s15_c0→b07_c0` 的 `target_pci` 留成舊值 **205**,cell 實際已是 **233**(`CASE=q10`) |
| **門檻** | `ANR_STALE_PCI_CHECK=on` → 依舊 PCI 找不到目標 → `CellNotAvailable` |
| **看什麼指標** | 失敗原因集中 `CellNotAvailable`;`REPORTCGI(205)` 解不到、`REPORTCGI(233)` 唯一解到 `b07_c0` |
| **平台解法** | **先刪後建**:`REMOVE` 舊關係 → `ADD` 帶新 PCI |
| **ACK** | `REMOVED` → `ADDED`,`storedPci` 由 205 變 233 |
| **驗收** | 換手成功率回升、關係 `targetPhysicalCellId=233` |

### Q11 老化 / 自動刪除 — `anr_stale_relation`

| 項 | 內容 |
|---|---|
| **怎麼觸發** | `CASE=q11` 建一筆 30 天前、零活動的關係,另建一筆 `noRemove` 保護條目 |
| **看什麼指標** | `relationAgeSec` 大 + 該筆 `att=0` + **`cumulativeSinceCreation` 也是 0**(三者同時才是真老化) |
| **平台解法** | `REMOVE` 老化零活動關係;對受保護條目**必須被拒** |
| **ACK** | 一般 `result=REMOVED`;受保護 `result=REJECTED_PROTECTED` |
| **驗收** | 老化關係消失、保護條目仍在且 version 不變 |
| **注意** | `cumulativeSinceCreation` 走 DB group-by(非近端 2000 筆切片),**舊證據不會被淘汰** —— 這是修過的 bug,否則會把「曾經用過」誤判成「從未用過」而錯刪 |

### Q12 NRT 屬性稽核(不動手) — `anr_attr_audit`

| 項 | 內容 |
|---|---|
| **怎麼觸發** | `CASE=q12` 讓 `s19_c0→d02_c0` 的 `isHoAllowed=false` —— 看似異常,但**有正當來源** |
| **看什麼指標** | `cumulativeSinceCreation` 空 vs 有值,可區分「從未用過」與「曾用過後被關掉」;`relationChangeEvents.by` 指出是誰改的(`xapp`/`gnb-xn`/`ANR`/`E2NodeAnrFunction`) |
| **平台解法** | **不動手** —— 有正當理由的屬性不得改;只做稽核 + SMO_NOTIFY |
| **ACK** | 無 ANR control |
| **驗收** | `changeEvents` 0、`by=xapp` 0、關係 version 全不變 |

## 2. 兩個對照劇本

### `anr_neutral_healthy` — 抓誤報用

全連通健康拓樸(h1/h2/h3、6 條關係)。十二支 guard 全常駐 21 分鐘的合格線:
`changeEvents=0`、`by=xapp=0`、關係 version 全 1、adapter ANR control=0,
**且 HO 仍 15/min**(證明場景是活的,不是死寂造成的假通過)。

### `anr_veto_variant` — 讓路仲裁

| 變體 | 主導 cause | 正解 | 驗收 |
|---|---|---|---|
| ① 該讓 | `CellNotAvailable` 100%,TooEarly=3.0 高於門檻 | 讓路,照常 REMOVE+ADD | 30 秒閉環;alarm 的 `exclusions` 記下被 bypass 的讀值 |
| ② 不該讓 | `HandoverToWrongCell` 100% | **不動手** + SMO_NOTIFY | 2 秒收手;changeEvents 0;關係全 v=1 |

此劇本刻意保留 **120m 密集間距 + 激進 A3(1.0/0.5dB/80ms)**,與其餘十二題不同。

## 3. ⚠️ 三個判讀陷阱(寫 guard 前必讀)

1. **`mroKpm.*Rate` 會自我抹除** —— MRO 判定某 RLF 為 ToWrongCell 後,backfill 把對應的成功換手改寫成 FAIL,下次查詢時該筆命中「更近的失敗嘗試優先 → 不做 MRO 歸因」而被跳過,速率歸零。
   **判 MRO 型病請用 `handoverFailureCauseRatePerMin` 的 cause 佔比,不要用 `mroKpm.*Rate` 當閘門。**
2. **被疾病污染的指標不能當排除閘門** —— 換手失敗型的病(Q6/Q7/Q10)會自己把 MRO 打高。
3. **止血曲線三陷阱** —— UE 靜止的假歸零、環境地板不是 0、空窗填充不等於衰減。詳見 [`README.md`](README.md) §5。

## 4. sim 能力邊界(劇本設計前必讀)

場景地面僅 ±500m;絕對稀疏 <1/min 做不到;`gap<0` 難以維持;cell 間距需 ≥300m
(A3 3dB 門檻下 150m 只有約 1.6dB 差,換手觸發不出來);`cellBarred` 有三條操作規則
(不可讓一個 cell 的所有鄰居都 barred,否則 UE 掉成永久 IDLE);劇本 duration 要開足
(≥7200s,建議 86400s),否則波形跑完 UE 靜止會造成假性平靜。完整十條見 [`README.md`](README.md) §4。
