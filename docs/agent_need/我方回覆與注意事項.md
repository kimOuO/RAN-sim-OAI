## 零、最重要的一件事：識別必須與 RIC 端一致

委託者已確認：**對方的 Agent 會依我方提供的識別，部署 xApp 到 RIC**。
xApp 的 E2 訂閱與 `RICcontrolRequest` 都以 `meid` + NR Cell Identity 定位，
因此我方對外宣告的識別若與 RIC 端實際看到的不同，xApp 會訂閱不到、控制打不中。

為此我方做了一項架構調整（✅ 已完成）：

> **場域（scene）釘住 E2 槽位（`e2_slot`）。**
> 槽位固定 → gNB ID 固定 → cell 標籤固定 → NR Cell Identity 固定，
> 於是整套 RIC 識別在模擬啟動前就能算出、且每次啟動都相同。

**代價（必須告知對方）**：
- **同一場域同時只能執行一場模擬**（不同場域各有槽位，仍可並行）。
  對應 I-1 之 `limits.concurrent_runs = 1`。
  同場域重複啟動會回錯誤，而非排隊。

## 二、與規格不同、需對方調整預期之處

### 1. 收集間隔是 1 秒，不是 60 秒 ❗

規格範例為 `granularity_period_s: 60`；我方實際 PM 視窗為 **1.0 秒**。

影響：
- 一次 900 秒的模擬，對方預期 15 窗，我方會產出 **900 窗**
- 「近 30 分鐘趨勢 = 6 窗」在我方是 1800 窗

處理方向（🔧）：原始觀測維持 1 秒窗，彙整觀測另做可設定的聚合層（預設 60 秒）。
請對方確認可接受。

### 2. `neighbour_relations` 是「宣告值」，不是執行期現況 ❓

I-2 回傳的是場景預先宣告的鄰區關係（registry 的 `NeighborSeed`）。
**執行期由 ANR 自主建立的關係不在其中**，那些請從 I-5 的當下觀測取得。

我方認為這樣分工正好符合對方的判準需求：
- I-2（宣告值）= 應有的關係
- I-5（觀測值）= 實際的關係
- 兩者相減 = ANR 新增或缺漏了什麼

若對方期望 I-2 直接回執行期現況，請告知，我方改以「上次 run 結束時的快照」提供。

### 3. 自主 ANR 會把「缺漏鄰區」自動補掉 ❗❗

我方 CU 具備自主 ANR（run knob `anr_auto_add`，預設開啟）。
它會在模擬進行中自行發現並建立鄰區關係。

**對類型二情境（例如「新增 cell 後鄰區關係缺漏」）這會破壞正確答案** ——
對方刻意留空的關係，會在數秒內被我方自動補上。

處理：I-3 觸發時可指定關閉（🔧 將開放為請求欄位）。
兩種用法都有意義：
- 關閉 = 缺陷持續存在，純考題
- 開啟 = 可觀察 SON 多久修復，屬另一類題目

相關的自主行為一律記入 I-7 組態變更紀錄，`origin` 標為 `son_function`。

### 4. 藍隊若直接操作 RIC，識別對照需併入題目 ❓

若藍隊在 RIC 主控台/xApp 上診斷，他們看到的是 `gnb_208_095_000e01` 與
`0xb2a9cd944`。題目若只寫 `src`，兩邊對不起來。
建議題目一併帶上 `ran_name` 與 `nr_cell_identity`。請對方確認驗證流程。

## 三、模式與倍速（I-1 `limits` / I-3）

| 模式 | 說明 | 限制 |
|---|---|---|
| `cached` | 通道預先以射線追蹤算好 | 可加速。實測 18 UE × 3 cell：**5× 達成 4.99×、量測報告零丟包**；**30× 僅達成 27.3×、丟失 1091 筆報告** |
| `live` | 即時射線追蹤 | **實測約 1× 實時**，固定 1×；**全系統同時只允許 1 個 live run**（Physics/GPU 共用） |

**改動 UE（新增/刪除/改路徑）會使通道快取失效**，該次模擬將強制切換為 `live`。
此時上述 live 限制全數適用。

註：倍速在 API 層並非硬性禁止，但超過上述實測值會造成量測報告稀疏，
我方前端已依此限制選項。

## 三之二、模擬保真度:與真實 RAN 的差異(請對方設計情境時納入考量)

我方多數機制都有實作,以下是**已知的簡化或未啟用項**。分三類:

### (a) 機制有做,但時間解析度受限 ❗

| 項目 | 真實 RAN | 我方 |
|---|---|---|
| 量測報告觸發 | UE 自行判斷 A3,條件成立才送(TS 38.331 reportConfig) | DU **每個 PM 視窗週期送**,A3 在 CU 端評估 |

原因:我方的 `GnbDuMeasurementReport` 同時扛 TS 28.552 的 PM 計數器(吞吐、PRB、
PDCP 量)與 TS 38.331 的無線量測(RSRP/RSRQ/鄰區)。PM 依定義必須週期上報,
量測便繼承了同一個節奏。

**實質影響**:PM 視窗預設 **1.0 秒**,而 A3 的 TTT 預設 80 ms ——
**TTT 的有效解析度是 1 秒**,設 80 ms 與設 800 ms 行為幾乎相同。
L3 濾波(k=4)同樣作用在秒級樣本上。

→ 若貴方要做「太早換手 / 太晚換手」這類需要次秒級時序的判定,請先告知,
我方需將量測與 PM 拆成兩條上報路徑。

A3 邏輯本身完整實作(TS 38.331 §5.5.4.4:offset / hysteresis / TTT / L3 濾波),
是否觸發可從 I-6 的 `ho_exe_succ` / `ho_exe_fail` 之 `payload.trigger`(值為 `A3_TTT`)看出。

### (b) 能力已具備,但本場域未啟用 ❓

| 項目 | 狀況 | 啟用代價 |
|---|---|---|
| **漫射散射** | `SIM_DIFFUSE_REFLECTION` 開啟且已傳給 Sionna,但**材質的 `scattering_coefficient` 從未設定**(Sionna 預設 0)→ 等同未開 | 需重算通道快取(24h 場域約 15 小時) |
| **多元件天線** | 已有 15 組 preset(含 64T64R)與路徑合成(`path_synth`,有對拍測試);但本場域三個 cell **未指定 preset**,落到 1×1 tr38901 | 同上。且換 preset 只影響 MIMO 通道矩陣,RSRP 仍讀 1×1 算好的快取,要一致必須重算 |
| **量測回報門檻** | `MEAS_REPORT_MIN_RSRP_DBM` 已實作,但**預設 −110 dBm 幾乎不過濾** —— 真實 UE 不會回報如此弱的鄰區 | 改參數即可,但會改變既有場景數據 |

**影響**:
- 漫射未開 → 走廊這類多反射環境的 NLOS 訊號偏低,覆蓋洞可能被高估
- 1×1 天線 → 無陣列增益與波束成形,`beam_id` / `beam_rsrp_top` 欄位存在但意義有限
- 門檻過鬆 → 「稀疏量測樣本」類情境做不出來

以上三項是否啟用請貴方告知需求,我方評估重算排程。

### (c) 尚未建模

| 項目 | 後果 |
|---|---|
| 功耗模型 | `PEE.AvgPower` / `PEE.Energy` 無法提供;節能類情境無法驗證 |
| cell 可用率 | `cellAvailablePer` 無 |
| `conn_release` 事件 | 連線釋放無紀錄 |
| measurement gap | 無量測間隙,UE 可「同時」量測所有頻點 |
| SIB1 讀取延遲 | CGI 解析為瞬時(可設失敗率,但無延遲) |
| 上行 MIMO | rank 固定為 1 |

### (d) 架構層落差

| 項目 | 說明 |
|---|---|
| **一個 run = 一個 E2 node** | registry 可畫多個 gNB,執行期會塌縮為單一 E2 node 下的多個 cell。跨 gNB 的 Xn 與換手在**資料上是完整的**,但 E2 拓樸上只有一個節點 |
| UE 軌跡寫定 | 見第六節負載型態 |
| 通道快取的 cell 維度固定 | cached 模式無法新增 cell(`cell_addition` 事件須走 live 模式) |

## 六、需對方決策：負載型態（`load_profiles`）❓

規格假設我方內建 `walk_normal` / `commute_flow` / `peak_hours` 等型態，
指定名稱與人數即可產生對應人流。

**我方架構不同**：UE 是每個場域寫死的路徑資料，無「型態」這層抽象，
亦無執行期人流生成能力。且通道快取以 UE 軌跡為索引
（`path_gain_db[tick, ue, cell]`），**換一組人流即快取失效**。

三種可行方向，成本差異極大：

| 方向 | 說明 | 成本 |
|---|---|---|
| A. 每型態預先算一份快取 | 一場域 × 三型態 = 三次射線追蹤預算 | 24 小時場域每次約 15 小時 |
| B. 改用 live 模式 | 人流可任意指定，不需預算 | 1× 實時、同時僅 1 場 |
| C. 一場域 = 一型態 | `load_profiles` 只回該場域實際具備者 | 零成本，但對方無法選型態與人數 |

請對方告知**實際需要幾種型態、各幾人**，我方據以評估。

## I-3 觸發情境 —— 已完成（2026-09-22）

路徑：`POST /api/v0.1/Run_orchestrator/Agent_api/ScenarioController/run`

### 可觸發的事件型別

型別**依場域與模式而定**，請以 I-1 的 `fields[].event_types` 為準，不要照規格
的完整清單出題。目前走廊三場域（cached 模式）可用四種：

| type | 做得到嗎 | 實作方式 |
|---|---|---|
| `cell_outage` | ✅ | DU `is_active=False`，tick 直接跳過該 cell；與 `PEE.cellAvailablePer` 同一機制 |
| `energy_saving_state` | ✅ | 同上開關。與 outage 對無線面影響相同，差別只在成因（由 I-7 的 `action_type` 分辨） |
| `tx_power_change` | ✅ | 發射功率是執行期疊到（快取的）path gain 上的，改得動。同時改 RU 與 DU 兩處 |
| `relation_change` | ✅ | CU 的 NrCellRelation，走與 xApp 相同的 SON 入口 |
| `cell_addition` | ⚠ 有條件 | 只能開啟「預算時已納入、初始關閉」的備用 cell。場域沒有備用 cell 時 I-1 不列此型別 |
| `antenna_change` | ✅ live／❌ cached | live 模式走即時射線追蹤，每 tick 重讀方位，改得動。cached 模式下方位已烘進通道快取，執行期改動不會改變任何 path gain，一律退回 |

**做不到的一律在啟動前退回**，不會靜默忽略。原因：貴方把請求原樣存成正確答案，
我方假裝做了而沒做，整份題目的答案就是錯的。

### `relation_change` 的屬性對映

規格用「允許」，我方內部存的是「封鎖」，語意相反，已在我方轉換：

| 規格 `attributes` | 我方旗標 | `true` → | `false` → |
|---|---|---|---|
| `is_ho_allowed` | `hoBlocklist` | clear | set |
| `is_remove_allowed` | `noRemove` | clear | set |
| `is_xn_allowed` | `xnBlocklist` | clear | set |

### cell 識別

`target` 收 I-2 的 `cell_id`（如 `src`）或 `ncgi`（如 `208095-56bce6561`），
兩種都可以。執行期的 cell_id 帶 E2 槽位標籤（`e03:src`），該標籤啟動後才確定，
貴方不需要知道，由我方轉換。未釘 `e2_slot` 的場域無法注入事件（識別無法事先決定），
會回 409。

### 時間

事件以**劇本時鐘**觸發，不是牆鐘 —— 我方支援倍速，30 倍速下牆鐘 12 秒就是劇本
360 秒。實測誤差 0.5～8 秒（輪詢間隔在倍速下的解析度），每筆的實際落點與誤差都記在
I-7 的 `landing_latency_ms`，請以該值核對而非假設精準。

`duration_s` 由我方在劇本時鐘到點時停止該次模擬（實測要求 420 秒、於 425.5 秒停止）。

### `duration_s` 不為 null 的事件會自動補還原

`cell_outage` 持續 120 秒 → 我方在 `at_offset_s + 120` 自動補一筆開站。
補出來的事件 `event_id` 為 `<原 id>~revert`，I-7 的 `detail.revert_of` 指回原事件。
不補的話貴方以為只關了兩分鐘、實際關到劇本結束，觀測資料與答案不符。
語意上不可還原的（如 relation remove）明確不補。

### 決定性（總則 7）

`seed` 會混進 DU slot 引擎的亂數種子（`seed × 1000003 + tick`）。
同一組參數 + 同一 seed 逐 tick 重現；換 seed 得到另一組雜訊實現。
通道為預算快取、UE 路徑為寫定資料，兩者本來就是決定性的。

### 未採用的參數

| 欄位 | 處理 |

| `ue_count` | **只能減少，不能增加**。小於場域人數時依 `seed` 決定性抽樣（同 seed 同一批），實際名單見 I-4 的 `ue_names`；大於場域人數回 400 並附 `max_ue_count`。<br>不能增加的原因：通道快取是 `path_gain_db[tick, ue, cell]`，UE 軸在預算時就寫死，新的人沒有任何傳播資料，要生出來只能捏造軌跡 |

## 順帶修正：觀測資料與事件的時間軸原本不同源（2026-09-22）

`RunKpmSample.scene_t_sec` 原本取自 UE 端的 `elapsed_sim_sec`，那是「牆鐘 × 設定
倍速」的推算；換手／RLF 事件用的則是 DU 的劇本時鐘。倍速達不到時兩者嚴重背離 ——
實測一場 DU 走了 904 秒、UE 端算成 3633 秒（近 4 倍）。

這會讓貴方無法把 I-5 的觀測與 I-6 的事件對到同一條時間軸上。已改為一律使用 DU 的
劇本時鐘（與 `sim_time_ms` 同源）。舊 DU 不帶該欄位時才退回原推算。

## 2026-09-22 補充:I-4 / I-6 的修正與 live 倍速上限
