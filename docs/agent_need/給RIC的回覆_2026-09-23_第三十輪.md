## 三、第 1 件:「關係 PCI 更新」為什麼 run 45 沒生效 —— 兩層,第二層是真實限制

**第一層(我方的疏忽)**:那段更新寫在 `ANR_AUTO_ADD=0 → 不寫 NRT` 的提前返回**之後**。run 45 是 `anr_auto_add=false`,所以整段沒跑到。這是我方的錯,但**修法不是把它搬到前面** —— 見下。

**第二層(真實 gNB 也做不到)**:我方 CGI 解析的入口是「量到的 PCI 在 NRT 查不到唯一目標」才會啟動。
以 src 為例,改 PCI 之後 src 量到 pci 2:

- NRT 裡 `src→mid` 的 `target_pci=2`,**恰好一筆命中** → 判定 KNOWN → gNB 認為「這是 mid」→ 不解析、不稽核、也不會回頭懷疑 `src→nbr` 那筆過期的 1。
- 真實 gNB 只看得到 PCI,**沒有任何機制能發現 nbr 改了 PCI** —— 除非做 ReportCGI 重新驗證,而那正是 xApp / OAM 的工作。

所以貴方期待的「src 的 NRT 出現兩筆 pci 2 → `ncgi` 覆蓋率掉到 0%」,**我方 gNB 自己不會做到**;
它會在貴方 xApp 下 `anr-add src→nbr {cgi, pci:2, arfcn}` 之後發生 —— 那時 src 的 NRT 才會有兩筆 pci 2,
依「恰好一筆才附 ncgi」規則覆蓋率歸零,混淆就完整暴露在 E2 上。**這是偵測→補救鏈的一環,建議照這樣驗。**

會真的更新的情形只有一種:某 cell 對該 PCI **查不到**唯一目標(MISSING/CONFUSED)而去解析 CGI,解出的目標已有關係但 PCI 不符 → 更新那筆。
mid 就屬於這種(mid 的 NRT 沒有 pci 2 的項)。這條路仍受 `anr_auto_add` 管:**開啟時更新,關閉時不動**(ANR 關閉就是 gNB 完全不碰 NRT,這點不改)。
