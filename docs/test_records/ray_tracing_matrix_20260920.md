# 射線追蹤設定矩陣 + RLF 歸因(2026-09-20)

## 起因

corridor_peak_2h run 1 出現 2,620 筆 RLF 對 915 次換手。初步觀察到通道快取的
路徑增益在相鄰 0.5 s 格之間擺盪逾 100 dB,推測是預算品質問題。

## 做了什麼

在 `osm_ntust_test` 的複本(`rt_probe_*`,1,200 ticks × 6 UE × 6 cell)上跑四組設定,
量三個穩定度指標,並對 TR 38.901 UMa 比絕對值。

| 設定 | NaN | 相鄰 tick p95 | p99.9 | max | 路徑損耗指數 n |
|---|---|---|---|---|---|
| 基線(現況) | 0.99% | 11.48 | 36.3 | 57.5 | 3.10 |
| `diffuse_reflection=off` | 0.99% | 11.29 | 36.4 | 57.5 | 3.09 |
| `samples_per_src=4e6` | 0.60% | 11.40 | 37.1 | 70.4 | 3.09 |
| 兩者 | 0.60% | 11.46 | 37.6 | 72.4 | 3.07 |

## 結論

**1. 絕對值沒問題。** 實測 path loss 對 TR 38.901 UMa NLOS 的中位差 **+0.8 dB**,
路徑損耗指數 3.10 落在 UMa LOS 2.20 與 NLOS 3.91 之間 —— 混合視距校園場景的合理位置。

**2. `diffuse_reflection` 一直是空轉的旗標。** Sionna 的 `RadioMaterial.scattering_coefficient`
預設為 0,沒有材質設過非零值,所以從來沒有產生過漫射路徑。關掉它統計數字幾乎不變。
（副作用:我們的場景完全沒有模擬漫射散射,陰影區沒有散射能量填底。這是獨立的建模缺口。）

**3. 提高取樣不改善穩定度。** NaN 從 0.99% 降到 0.60%(找到更多路徑),但跳動的尾巴
反而略微變長 —— 多找到的是門檻邊緣的弱路徑,這格有下格沒有,反而增加跳動。
代價是 4 倍預算時間。**不建議採用。**

**4. 原始快取的跳動不是模擬看到的東西。** DU 在載入時就做 gap-fill(≤30 s)與
10 秒移動平均(`channel_cache_du.py` `fill_path_gaps` / `smooth_path_gain`)。平滑後:

| 場景 | 原始 p99.9 | 平滑後 p99.9 | 填地板(無路徑 >30 s) |
|---|---|---|---|
| corridor_00_08 | 43.7 dB | **4.9 dB** | 593,116 格(28.6%) |
| corridor_peak_2h | 108.2 dB | **7.6 dB** | 13,766 格(2.7%) |
| osm_ntust_test | 36.3 dB | 9.3 dB | 0 |

**5. 通道無法解釋 RLF 數量。** 以平滑後快取 + 滿載最壞干擾推算 corridor_peak_2h:
SINR 低於 −6 dB 的時間佔 0.72%,共 226 段(中位 3.5 s,最長 12 s),
其中撐過 N310 偵測 + T310(1000 ms)而應判 RLF 的只有 **157 段**。
實際歸檔 **2,620 筆**,相差 **17 倍**。

→ **RLF 過度觸發的原因在 RAN 側的 RLF 判定邏輯,不在射線追蹤。**

## 兩個先前對外說過、但錯誤的歸因

1. 「RLF 來自漫射取樣的蒙地卡羅雜訊」——錯,漫射從未生效(見結論 2)。
2. 「RLF 來自快取的相鄰格跳動」——錯,模擬吃的是平滑後訊號(見結論 4)。

兩者都已向 RIC 更正。教訓:量到現象(跳動是真的)不等於找到成因,
對外歸因前要先驗證該機制確實在作用路徑上。

## 下一步

查 RLF 判定鏈:DU 算出的 SINR → CU 的 T310 狀態機(Qout/Qin、N310/N311)。
重點是確認判定吃的是哪個值、以及 out-of-sync 的評估週期是否符合 TS 38.133。
**不需要重算任何通道快取。**

## 產物

- 評估腳本:`tools/rt_eval.py`(穩定度 + TR 38.901 InH/UMa 對照)
- 實驗場景:registry 的 `rt_probe_base` / `_nodiff` / `_4x` / `_both`,可刪

# 續:RLF 歸因第二輪(同日)

## 從 corridor_peak_2h run 1 的歸檔量到的

| 觀察 | 數值 |
|---|---|
| RLF 當下,服務 cell RSRP | 中位 −50 dBm(p05 −87) |
| RLF 當下,最佳鄰區 RSRP | 中位 −54 dBm |
| RLF 當下,KPM 回報 SINR | 中位 +10.5 dB |
| 服務 RSRP < −110 的比例 | 1.3%(兩邊都 < −110:0.0%) |
| `sinr_at_rlf` 分布 | −7 ~ −25 dB 散布;恰為 −30(無服務哨兵)的僅 0.2% |
| KPM SINR < −6 dB 的樣本比例 | 4.19% |
| RLF 當下鄰區比服務好 > 3 dB | 27.0%(中位是鄰區比服務**差** 6.9 dB) |
| 全場兩 cell RSRP 差在 ±6 dB 內 | 30.3% |

## 可以排除的

- **不是覆蓋洞**:RLF 當下 RSRP 中位 −50 dBm,兩邊都低於 −110 的情形是 0%。
- **不是「換手來不及」為主因**:只有 27% 的 RLF 當下存在可換的較佳鄰區(> 3 dB)。
- **不是狀態機邏輯壞掉**:`sinr_at_rlf` 是連續散布的真實低值,不是固定哨兵值;
  `rlf_detector.py` 的 N310 / T310 / N311 實作對齊 TS 38.331。
- **不是通道快取**:見上半部,平滑後 p99.9 僅 7.6 dB。

## 目前最合理的解釋(尚未量測證實)

RLF 判定吃的是**每 tick 的瞬時 SINR**(`tick_runner._feed_rlf` → `ue["sinr_db"]`),
KPM 記的是 **1 秒視窗平均**(PM aggregator)。快取平滑 ⇒ 瞬時值的劇烈起伏是在
SINR 計算階段產生的,最可能來自干擾項:

走廊兩個 cell 同頻且重疊嚴重(30.3% 的時間 RSRP 差在 ±6 dB 內)。C/I 只有幾 dB 時,
每 tick 的 PRB 負載變動就足以讓 SINR 在 +10 與 −10 之間擺盪。peak_2h 的 PRB 佔用
64–86%,而 run 7 前段無流量時幾乎不 RLF、一有負載就暴增 —— 與這個機制一致。

## 怎麼證實(下一步)

在一次短跑中同時記錄餵給 `RlfDetector.observe()` 的瞬時 SINR 與同 UE 的 KPM 視窗值。
兩者若相差顯著,即證實;再看瞬時值的變異是否隨 `cell_dl_load` 變動。
**現有歸檔沒有瞬時值,無法回溯驗證。**

## 若成立,處置方向(先不動手)

1. RLF 判定改吃短視窗平均(TS 38.133 的 out-of-sync 評估本來就是 200 ms 窗,不是瞬時)。
2. 走廊場景兩 cell 的重疊本身也值得檢討(同頻、同功率、無方位/傾角隔離)。

兩者性質不同:1 是模擬保真度問題,2 是場景設計問題。不要混為一談。

# 續二:RLF 歸因結案(同日,07:07–07:19 UTC 的 RLF_TRACE 短跑)

## 做法

在 `tick_runner._detect_rlf` 加 `RLF_TRACE=1`(預設關),把餵給
`RlfDetector.observe()` 的**瞬時** SINR、RSRP 與當下 `cell_dl_load` 逐 tick 印出。
corridor_peak_2h 跑 12 分鐘(2× 速),收到 51,209 筆。

## 結果

**1. 「瞬時值比視窗值狂野」的假設不成立。**

| | 瞬時(RLF 吃的) | KPM 視窗平均 |
|---|---|---|
| SINR < −6 dB 的比例 | 3.32% | 4.19% |
| 相鄰 tick \|Δ\| 中位 | 0.14 dB | — |
| 相鄰 tick \|Δ\| p95 | 3.9 dB | — |

**2. RLF 判定機完全正確。** 拿 trace 重跑狀態機(Qout −6 / Qin −4 / N310 2 / N311 2 /
T310 1000 ms)預期 **415** 次,DU 實際宣告 **398** 次,差 4%(差異來自 UE 進出 registry)。

**3. 低 SINR 的條件是「弱訊號點 + 高負載」同時成立。**

| | PRB 負載中位 | RSRP 中位 | 樣本 |
|---|---|---|---|
| SINR < −6 dB | **0.949** | −67.2 dBm | 1,700 |
| SINR ≥ −6 dB | 0.777 | −49.0 dBm | 49,509 |

## 結論

**沒有 bug。**走廊場景的 RLF 數量是以下三者的忠實結果:

1. 兩個 cell 同頻、同功率、無方位/傾角隔離,全場 30.3% 的時間 RSRP 差在 ±6 dB 內;
2. 尖峰時段 PRB 負載達 95%,鄰區干擾接近滿功率;
3. Qout −6 dB / T310 1000 ms 的判定門檻(對齊 TS 38.331 預設)。

干擾受限的重疊佈設在高負載下本來就會頻繁失聯。**這是場景佈設的結果,不是模擬錯誤。**

## 對外說法要更正(第三次,方向相反)

先前告訴 RIC「走廊系列的 RLF / 換手不可用於品質評估」。依本輪證據,
**該結論應予撤回** —— 資料忠實反映了一個重疊嚴重且過載的兩 cell 佈設。
可用,但解讀時要知道它描述的是這個佈設,不是通則。

## 這輪的方法教訓

同一個問題連續三個假設(漫射雜訊 / 快取跳動 / 瞬時值抖動)都被自己的量測推翻。
共通錯誤:**看到現象就找一個看似合理的機制,沒有先確認該機制在作用路徑上、
且量級足以解釋觀察到的數量。**有效的做法是最後那一步做的:
直接量作用路徑上的輸入,再用它重跑判定邏輯,對回實際計數。
