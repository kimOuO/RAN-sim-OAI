# 資料品質公告:走廊場景 2026-09-19 17:00 UTC 前的數據不可用於品質評估

## 發生什麼

DU 在 cached 模式自行計算 SINR 時,cell 名稱轉成快取鍵的規則只認 `xxx_c<N>` 命名。
走廊場景的 cell 叫 `src` / `nbr`,轉出來是 `src`,但快取的鍵是 `src#0` —— **永遠對不上**。
程式在對不上時會退回「用訊號最強的 cell 計算」。

結果:**UE 掛在已經沒訊號的 cell 上,SINR 卻回報最強 cell 的值。**

最嚴重的不是數值偏高,是**它讓故障完全隱形**:
- SINR 永遠漂亮 → RLF 門檻(−6 dB)從不觸發 → UE 卡在死掉的 cell 上
- KPM、監控頁、送給 RIC 的資料都看起來正常

修正:commit `67663f0`(2026-09-19)。cell→tx 改以載入的快取實際 tx 名為準;
服務 cell 真的沒有路徑時回 `DU_NO_SERVING_SINR_DB`(−30 dB),不再偷換 cell。

| corridor_00_08 `…8649117e33` | 1+ | — | 09-19 17:00 之後 | 正常 |

查詢時:
- `RunKpmSampleReader/read` **預設只回最近一次執行**(run_seq 最大者),走廊場景下就是修正後的資料
- 要明確排除舊資料:`run_seq=<最新值>`;或用 `run_kpm_sample_created_at >= '2026-09-19T17:00Z'`
- 注意 `run_seq` 的兩種意義:**存起來**的歷史資料(修正前、未分次)其 `run_seq` 欄位是 `0`;
  但查詢時**傳** `run_seq=0` 意思是「不過濾、全部都回」。要只看歷史資料請改用時間條件。

**RIC 端**:已同步標記。他們的 bug 簽名查詢是「RSRP ≤ −120 且 SINR ≥ 20」,
走廊各 run 命中 10–25%,修正後為 0%。
