# CCO 情境故事 — 容量受限換手（負載平衡 · 營運商視角）

> 給開發者理解 CCO 場景用，但**用營運商的視角與白話**講：環境出了什麼事 → 數據長什麼樣 →
為什麼要這個 xApp → 何時出手、做什麼、預期結果、怎麼看成效 → 使用者實際怎麼跟系統對話。
> 

---

## 1. 一句話故事

一個使用者位在兩個 cell 的覆蓋交界處，目前掛在 **Cell 0**。Cell 0 容量吃緊（資源已貼著上限），
當這個使用者把流量需求拉高時，Cell 0 **餵不飽** —— 吞吐被壓在低檔、資料開始排隊延遲；但旁邊的
**Cell 1 其實還很空**。我們希望系統能**自動認出這種容量受限**，把使用者**換手到還有餘裕的 Cell 1**，
讓體感速率立刻回升。營運商在生成 xApp 時就確認過策略，之後它就自主運作。

---

## 2. 環境發生什麼事

兩個 cell（A、B）覆蓋重疊，有個使用者在交界處。平時流量小、掛在 Cell 0 沒問題；一旦使用者開始
要大流量，Cell 0 的資源就見頂、餵不滿這個需求，但 Cell 1 還有大量空間沒被使用。問題是 —— 目前
沒有自動機制去「認出某個 cell 容量吃緊、而鄰居還很空」並把使用者移到更合適的 cell。

> 本 PoC 全網只有 1 個 UE；為了重現「容量受限的 Cell 0」，先把 **Cell 0 的 PRB 上限設成 20%**
（Cell 1 不設限）。真實網路裡這種受限通常來自 Cell 0 同時擠了很多使用者 —— 這裡用配額上限模擬。
> 

---

## 3. 數據長什麼樣（可偵測的徵兆）

容量受限會讓 Cell 0 的幾個指標呈現「有需求、卻被資源卡住」的組合：

| 指標 | KPM 欄位 | 代表意思 | 受限徵兆 |
| --- | --- | --- | --- |
| 下行資料量 | `DRB.PdcpSduVolumeDL` | 這個 cell 正在送多少下行使用者資料（代表有實際需求） | 高（使用者要大流量） |
| 無線資源使用率 | `RRU.PrbTotDl` | 無線資源被佔用的比例 | 貼著 Cell 0 的 20% 上限（撞頂） |
| 下行延遲 | `DRB.RlcSduDelayDl` | 資料在 cell 端排隊等送的時間 | 開始累積、上升 |

**判讀**：Cell 0 **有需求（資料量高）但資源撞頂、吞吐上不去**，同時**鄰居 Cell 1 明顯比較空**
→ 這是容量受限、該把使用者移到還有餘裕的 cell（而不是干擾或低載問題）。

---

## 4. CCO xApp 怎麼介入

```
何時出手  使用者在 Cell 0 把需求拉高、Cell 0 資源撞上限、吞吐上不去，且鄰居 Cell 1 明顯較空
做什麼    把這個使用者 handover 到容量充足的 Cell 1
怎麼運作  上線後自主判斷、自主出手，不需逐次人工確認
何時收手  使用者已到 Cell 1、吞吐回升、需求被滿足 → 條件解除，不再重複換手
```

- **要比較才換**：必須確認鄰居 cell 確實比較空才換手，否則白換（避免換到另一個也滿的 cell）。
- **自主換手**：同意點落在「生成 / 模擬確認」階段 —— 營運商事先看過它會在什麼條件、把誰換到哪；
上線後即時偵測、即時換手。安全性靠**事前模擬 + 條件把關 + 換手後自動停手**保證。

---

## 5. 預期結果與成效監控

| 維度 | 預期結果 | 怎麼看 |
| --- | --- | --- |
| 換手 | 使用者從 Cell 0 移到 Cell 1 | 該使用者在 Cell 0 消失、在 Cell 1 出現 |
| 容量改善 | 使用者吞吐跳升、排隊延遲回落 | 換手前後的吞吐 / 延遲對比 |
| 資源釋放 | Cell 0 資源被釋出 | Cell 0 的資源使用率 / 吞吐回到低檔 |

> 單 UE 環境下，實際看到的是 **A→B 的角色互換**（不是多用戶真正負載趨平）；但「受限 → 換手 →
吞吐回升」的因果在 KPM 上看得清楚，足以證明 RC 有效。
>
